# Repository Guidelines

## Project Structure & Module Organization

Weigh Together is a two-module Kotlin/Gradle Android project. `app/` contains Compose UI, BLE scanning, Room persistence, WorkManager jobs, and Health Connect integration. Production code is under `app/src/main/kotlin/`; JVM tests are in `app/src/test/`, device tests in `app/src/androidTest/`, and resources in `app/src/main/res/`. Version Room schemas in `app/schemas/`.

`core/` is the platform-independent parsing and body-composition library. User setup is in `README.md`. Do not create separate plan files unless the user explicitly requests one; record task planning in the relevant GitHub issue.

## Build, Test, and Development Commands

Use JDK 17 and Android SDK Platform 36; set `sdk.dir` in untracked `local.properties`.

- `./gradlew testDebugUnitTest` runs app JVM tests.
- `./gradlew :core:test` tests packet parsing and calculations.
- `./gradlew lintDebug` runs Android lint.
- `./gradlew assembleDebug` creates the normal debug APK.
- `./gradlew connectedDebugAndroidTest` runs instrumentation and Compose UI tests on a connected emulator or device.

Before opening a PR, run the combined check documented in the README: `./gradlew testDebugUnitTest lintDebug assembleDebug`.

Before building an APK, delete the previous APK artifact for the target build type from `app/build/outputs/apk/<buildType>/`; do not delete unrelated build outputs. Every ordinary final APK build must increment Android `versionCode` and keep `versionName` unchanged. Change `versionName` only after an explicit owner decision to create a release, using the `0.1.<release>` format. Commit the applicable version changes with the final build; the target-artifact cleanup and commit requirements apply to both ordinary builds and releases.

## Coding Style & Naming Conventions

Follow existing Kotlin style: four-space indentation, trailing commas in multiline declarations, and package names rooted at `com.palixander.weightogether`. Use `UpperCamelCase` for classes/composables and `lowerCamelCase` for functions/properties. Keep domain logic out of Compose screens; place persistence in `data`, synchronization in `sync` or `worker`, and reusable UI in `ui`. No formatter is configured, so use IDE Kotlin formatting and clean imports.

## Testing Guidelines

Tests use JUnit 4/Kotlin Test plus AndroidX, Room, WorkManager, and Compose test libraries. Name files `*Test.kt` and methods as behavior statements, such as `repeatedPacketIsStoredAndScheduledOnlyOnce`. Prefer JVM tests for pure behavior and instrumentation tests for migrations, WorkManager, or Compose. No coverage threshold is enforced; every fix should include regression coverage. Commit schema updates with migrations.

## Commit & Pull Request Guidelines

Use short, imperative commit subjects and append the related GitHub issue number in parentheses: `Fix chart marker overlay layout (#42)`. Optional `fix:` or `feat:` prefixes remain acceptable, for example `fix: validate scale identity (#42)`. Every task commit must reference its issue; keep commits focused. Do not use `Fixes #42`, `Closes #42`, or `Resolves #42` in ordinary commits because GitHub can close the issue when such a commit reaches the default branch. Issue closure remains part of the regulated post-review workflow. PRs should explain impact, list verification commands/devices, link issues or plans, and include screenshots for Compose changes. Call out migrations, permission changes, and flavor-specific behavior.

## Security & Configuration

Never commit `local.properties`, credentials, health data, or device identifiers.

## Регламент работы с задачами GitHub

### Общие положения

- Для любых операций с GitHub сразу использовать подключённый GitHub-плагин. Не проверять наличие GitHub CLI (`gh`) и не использовать его как предварительный или резервный способ доступа, если пользователь явно не потребовал обратного.
- Владелец заранее и явно разрешил отправлять task-ветки этого checkout командой `git push` в настроенный `origin` (`ilguit/ScaleSync`). В рамках шага передачи проверенной задачи в QA также заранее разрешён push интеграционного merge-коммита в `origin/main` после успешного независимого ревью и предусмотренных итоговых проверок. Для этих push не запрашивать повторное подтверждение; разрешение не распространяется на другие remotes, репозитории или иные изменения `main`.
- Источником требований является GitHub issue.
- Планирование, результаты исследования, резюме реализации и замечания ревью сохраняются в комментариях issue.
- Отдельные файлы планов в репозитории не создаются, если пользователь явно не попросил об этом.
- Процессные метки: `In Progress`, `Design`, `Design Review`, `Design Ready`, `Planning`, `Plan Ready`, `Coding`, `Ready for Review`, `Code Review`, `Need Fix`, `QA`, `Done`.
- Метки приоритета: `Priority: Blocker`, `Priority: High`, `Priority: Medium`, `Priority: Low`.
- Классификационная метка `Design Needed` означает, что пользовательский дизайн ещё не утверждён. Она не является ни процессной меткой, ни меткой приоритета.
- Классификационная метка `Technical` с описанием «Техническая задача: не включать в release notes» не является ни процессной меткой, ни меткой приоритета. Её используют только для задачи, которая целиком не имеет пользовательски заметного результата.
- Если задача уже помечена меткой `Technical`, считать классификацию подтверждённой: не пересматривать её и не снимать эту метку в рамках дальнейшей работы над задачей.
- Пользовательскую видимость определяют при оформлении задачи или не позднее стадии `Planning`, до перехода в `Coding`. Для полностью технической задачи ставят `Technical`; смешанной задаче с пользовательски заметной частью эту метку не ставят, а для пользовательской части создают пользовательский release-note fragment.
- GitHub label используется только для классификации и не является входом сборки. Исключение технической задачи из release notes подтверждается отслеживаемым Git-фрагментом по контракту `.release-notes/README.md`, без обращения к GitHub API.
- При оформлении задачи необходимо выбрать ровно одну метку приоритета. Альтернативные обозначения, включая `P0`, `P1`, `P2` и `P3`, не используются.
- При изменении приоритета старую метку следует заменить новой напрямую, не оставляя задачу без метки приоритета и не назначая несколько приоритетов одновременно.
- Одновременно у задачи должна быть только одна метка, обозначающая текущую стадию процесса.
- При снятии процессной метки, если в тот же момент не устанавливается другая процессная метка, обязательно поставить `In Progress`. Issue не должен оставаться без процессной метки в промежуточном состоянии.
- При установке любой процессной метки, кроме `In Progress`, метку `In Progress` необходимо сразу снять. Переход между стадиями следует по возможности выполнять как прямую замену одной процессной метки другой.
- Новая задача — открытый issue без процессных меток.
- После выставления `Need Fix` автоматически продолжать новый цикл планирования и исправления, если требуемое решение однозначно следует из замечаний ревью, требований issue и актуального плана. Приостанавливать работу и спрашивать пользователя только тогда, когда дальнейшая реализация зависит от его выбора между несколькими допустимыми вариантами или требует изменения согласованных требований.
- Под отдельным рабочим пространством понимается Git-ветка и worktree, а не новый GitHub-репозиторий.
- Для каждой задачи на стадии `Planning` определить видимость и тип будущего release-note fragment: пользовательский (`text`) или технический (`reason`), а также при необходимости затрагиваемые flavors. Файл фрагмента на стадии `Planning` не создавать.
- Во время `Coding` создать отдельный фрагмент по контракту `.release-notes/README.md`. При повторной работе обновлять существующий фрагмент; дополнительный фрагмент того же issue создавать только для отдельного пункта релизных заметок.

### Оценка токенозатратности

- Метки сложности: `Complexity: Low`, `Complexity: Medium`, `Complexity: High`, `Complexity: Extreme`.
- Одновременно у issue может быть не более одной метки сложности. При изменении оценки старую метку необходимо заменить новой напрямую.
- Оценка выполняется только по явному запросу пользователя и вне стадии `Planning`. Наличие готового плана и метки `Plan Ready` не является обязательным.
- На стадии `Planning` токенозатратность не оценивается. Планирование нельзя расширять дополнительным исследованием ради оценки.
- До `Planning` допускается предварительная оценка по описанию issue, актуальным комментариям и минимальному целевому read-only исследованию текущего кода. Такая оценка должна содержать уровень уверенности и не должна превращаться в полноценное планирование.
- Если в issue уже опубликована **Предварительная оценка**, на стадии `Planning` необходимо учитывать её выводы, выявленные компоненты, риски и результаты исследования, чтобы не повторять выполненную работу и экономить токены. Саму категорию сложности во время `Planning` не пересчитывать.
- После `Plan Ready` допускается уточнённая оценка по готовому плану и уже полученным результатам исследования. Код повторно не исследуется, если план достаточно конкретен; дополнительное чтение допускается только при существенном пробеле, не позволяющем определить категорию.
- Если готовый план уже существует, он используется как основной источник, но ради оценки нельзя отдельно запускать или повторять стадию `Planning`.
- Учитывается полный цикл задачи по всем агентам: уже выполненное планирование, реализация, передача контекста, тесты и сборки, анализ ошибок, итоговая проверка, независимое ревью, GitHub-операции и резерв на неопределённость. Параллельная работа не считается экономией токенов.
- Если доступна фактическая статистика, учитываются входные токены, включая кэшированные, и выходные токены. Reasoning-токены отдельно повторно не прибавляются, если они уже входят в выходные или общие токены.
- Категории определяются по верхней границе ожидаемого полного расхода с учётом резерва:
  - `Complexity: Low` — до 500 000 токенов включительно; резерв 15%.
  - `Complexity: Medium` — свыше 500 000 до 2 000 000 токенов включительно; резерв 25%.
  - `Complexity: High` — свыше 2 000 000 до 5 000 000 токенов включительно; резерв 40%.
  - `Complexity: Extreme` — свыше 5 000 000 токенов; резерв 50%.
- Если диапазон пересекает границу категорий, выбирается более высокая категория.
- Для `Complexity: Extreme` обязательно предложить декомпозицию или сокращение объёма. Не начинать реализацию без отдельного решения пользователя.
- Результат оценки публикуется отдельным комментарием в issue и содержит категорию, полный диапазон, приблизительный оставшийся расход, уверенность, основные факторы и риск перехода в следующую категорию. После публикации issue назначается соответствующая метка сложности.
- Если фактическая работа достигает 80% верхней границы, а обязательные этапы ещё не завершены, сообщить о риске превышения и пересчитать категорию только после подтверждения пользователя.

### Проработка UI/UX-дизайна

#### Когда требуется дизайн-стадия

Дизайн-стадия обязательна для задачи с меткой `Design Needed`. Она предшествует обычному техническому `Planning` и не заменяет его.

В дизайн-проработку можно взять:

1. Новую задачу с меткой `Design Needed` без процессной метки.
2. Задачу, возвращённую из `Design Review` в `Design` для устранения замечаний.

Перед началом поставить процессную метку `Design`.

#### Источники требований

Источником требований остаётся GitHub issue. Учитываются описание и все последующие содержательные комментарии; последние явно согласованные решения имеют приоритет.

Исследования, варианты, wireframes, результаты интервью, замечания design review и итоговая дизайн-спецификация публикуются комментариями issue. Временные интерактивные прототипы не являются самостоятельным источником требований.

#### Допустимые действия на стадиях Design и Design Review

Разрешены:

- продуктовые вопросы и фиксация решений в issue;
- read-only исследование существующего UI, архитектуры, тем, ресурсов и бизнес-логики;
- текстовые wireframes;
- создание и итеративное изменение прототипов, изображений и других дизайн-материалов во временном thread-scoped каталоге вне checkout;
- обновление комментариев и меток issue.

Запрещены:

- изменения любых файлов внутри checkout;
- изменения кода, ресурсов, тестов и конфигурации проекта;
- создание task-ветки или worktree;
- commits, merge и push.

Если применяемый skill требует немедленно изменить `CONTEXT.md`, ADR или другой файл репозитория, на дизайн-стадии выполняется только аналитическая часть. Предлагаемые доменные решения фиксируются в issue. Изменение документации переносится в отдельный шаг `Coding` либо в отдельную GitHub-задачу.

#### Обязательное содержание дизайн-проработки

Для задачи необходимо определить:

- scope и non-scope;
- информационную архитектуру и навигацию;
- структуру и назначение экранов;
- основные пользовательские сценарии;
- тексты, названия и терминологию;
- сохраняемую бизнес-логику и ограничения;
- визуальные правила и связь с существующей темой приложения;
- различия между затронутыми flavors;
- критерии визуальной и функциональной приёмки.

Для каждого затронутого экрана рассматриваются, где применимо:

- normal, empty, loading, unavailable и error states;
- обычная и узкая ширина;
- длинный текст и увеличенный системный шрифт;
- все затронутые flavors;
- навигация, подписи, контраст, touch targets и screen reader semantics;
- опасные действия, подтверждение и восстановление после ошибки.

Неприменимые состояния явно отмечаются в спецификации.

#### Design Review

После подготовки согласованного варианта:

1. Опубликовать в issue отдельный комментарий `Design specification`.
2. Заменить `Design` на `Design Review`.
3. Назначить нового агента, не выполнявшего основную дизайн-проработку.
4. Проверить полноту сценариев и состояний, соответствие существующему UI, теме, flavors, accessibility-требованиям и сохранение согласованной бизнес-логики.
5. Опубликовать замечания или подтверждение проверки в issue.

При замечаниях заменить `Design Review` на `Design` и продолжить проработку.

При отсутствии замечаний получить явное подтверждение пользователя в issue. До такого подтверждения дизайн не считается утверждённым.

#### Переход в Design Ready

После явного утверждения пользователем:

1. Снять `Design Needed`.
2. Заменить `Design Review` на `Design Ready`.
3. Перед созданием task-ветки получить актуальные изменения и синхронизировать локальную `main`.
4. Создать task-ветку от актуальной `main` и отдельный worktree.
5. Перенести утверждённые дизайн-артефакты в `docs/design/<issue-number>/`.
6. Назначить нового агента для проверки соответствия публикуемого пакета утверждённой спецификации.
7. Сделать отдельный commit с номером issue и push task-ветки.
8. Опубликовать в issue commit permalink на дизайн-пакет.
9. Заменить `Design Ready` на `Planning`.

На стадии `Design Ready` разрешены изменения только внутри `docs/design/<issue-number>/`. Код приложения, ресурсы Android, тесты, build-конфигурация, `CONTEXT.md`, ADR и другие файлы менять запрещено.

Task-ветка и worktree сохраняются и позднее используются для реализации этой же задачи.

### 1. Планирование

#### Выбор задачи

В планирование можно брать:

1. Новую задачу без процессных меток.
2. Задачу с меткой `Need Fix`: сразу, если исправление однозначно; после ответа пользователя, если дальнейшая реализация зависит от его выбора.
3. Задачу с завершённой дизайн-проработкой после публикации утверждённого дизайн-пакета и замены `Design Ready` на `Planning`.

#### Источники информации

Для новой задачи учитываются описание issue и все последующие содержательные комментарии; последние уточнения имеют приоритет над более ранними требованиями.

Для задачи с `Need Fix` учитываются замечания последнего ревью, все последующие комментарии, актуальная часть предыдущего плана и, если он требовался, выбор пользователя по неоднозначным вариантам исправления. Явно заменённые планы, решения и замечания считаются историей.

Для задачи с завершённой дизайн-проработкой последняя актуальная `Design specification` и ссылка на опубликованный дизайн-пакет являются обязательными источниками требований. Технический план должен сопоставить каждый критерий дизайн-приёмки с шагом реализации, тестом или явной проверкой и не должен самовольно пересматривать утверждённые продуктовые и UX-решения.

#### Порядок работы

1. Для задачи с `Need Fix` снять эту метку.
2. Поставить `Planning`.
3. Исследовать проблему.
4. Определить причину или вероятный источник, затрагиваемые компоненты, шаги реализации, независимые подзадачи, тесты, проверки и критерии готовности.
5. Опубликовать план отдельным комментарием в issue.
6. Снять `Planning` и поставить `Plan Ready`.

На стадии `Planning` запрещены изменения рабочих файлов, реализация, создание новых реализационных веток и worktree, коммиты, merge и push. Разрешены только read-only исследования и обновление issue. Ранее созданные на `Design Ready` task-ветка и worktree сохраняются без изменений.

### 2. Внесение изменений

#### Начало работы

1. Прочитать последний актуальный комментарий с планом.
2. Убедиться, что задача имеет метку `Plan Ready`.
3. Убедиться, что пользовательская видимость определена до перехода в `Coding`: полностью техническая задача имеет метку `Technical`, а пользовательская или смешанная задача её не имеет.
4. Снять `Plan Ready` и поставить `Coding`.
5. Если task-ветка и worktree уже созданы на `Design Ready`, заново получить с GitHub все актуальные изменения и синхронизировать локальную `main`, затем проверить, что task-ветка содержит только утверждённый дизайн-пакет, и актуализировать её относительно синхронизированной `main`. Первый реализационный шаг при необходимости включает согласованные изменения `CONTEXT.md` или ADR.
6. Для задачи без дизайн-стадии перед созданием новой ветки получить с GitHub все актуальные изменения, обновить локальную `main` относительно удалённого репозитория и только после успешной синхронизации создать отдельную task-ветку и worktree.

После `Need Fix` использовать существующую ветку задачи, если она ещё не слита или не удалена.

#### Выполнение плана

- Разбить основную задачу на последовательные шаги согласно плану; каждый шаг выполняет новый агент.
- Передать агенту актуальный план, состояние ветки, резюме предыдущего агента и критерии готовности шага.
- Агент работает только в назначенной ветке и worktree.
- После шага агент выполняет предусмотренные проверки, делает отдельный коммит при наличии изменений, не создаёт пустых коммитов и передаёт краткое резюме с проверками и ограничениями.
- Каждый коммит по задаче содержит ссылку на её GitHub issue в конце темы: `Краткое действие (#<номер>)`. Closing keywords (`Fixes`, `Closes`, `Resolves`) в обычных коммитах не используются, чтобы issue не закрылся до завершения ревью и финального этапа регламента.

#### Параллельные подзадачи

1. Для каждой независимой подзадачи создать отдельную ветку от ветки основной задачи и отдельный worktree.
2. Выполнять независимые подзадачи параллельно, разбивая каждую на последовательные шаги и назначая новый агент на каждый шаг.
3. Каждый агент коммитит только в ветку своей подзадачи.
4. После завершения назначить нового интеграционного агента: он мержит ветки подзадач в основную ветку задачи, разрешает конфликты, проверяет совместную работу, запускает общие тесты и при необходимости создаёт интеграционный коммит.

#### Завершение Coding

После выполнения плана отдельный агент должен:

1. Проверить release-note fragments командой `.github/scripts/validate-release-note-fragments.sh`, затем выполнить остальные итоговые проверки ветки задачи.
2. Определить диапазон ревью: в первом цикле — от точки расхождения с `main` до текущего HEAD; в повторном — от последнего проверенного SHA до текущего HEAD.
3. Опубликовать в issue краткое резюме, название ветки, начальный и конечный SHA, выполненные тесты и проверки.
4. Запушить ветку задачи.
5. Снять `Coding` и поставить `Ready for Review`.

### 3. Ревью изменений

#### Начало и проведение ревью

1. Убедиться, что задача имеет `Ready for Review`.
2. Снять `Ready for Review` и поставить `Code Review`.
3. Назначить нового агента, не выполнявшего проверяемые шаги реализации.
4. Прочитать последнее резюме и проверить явно указанный диапазон SHA.

Ревью проверяет соответствие issue и актуальному плану, корректность логики, регрессии, пограничные случаи, достаточность тестов, результаты сборки и отсутствие посторонних изменений. При необходимости проверяется взаимодействие с существующим кодом. Для задачи, прошедшей дизайн-стадию, ревью также сравнивает реализацию с последней утверждённой `Design specification`, сохранённым дизайн-пакетом и обязательной матрицей visual/accessibility/flavor states. Расхождение без последующего явного согласования считается замечанием. После ревью снять `Code Review`.

#### Если найдены замечания

1. Опубликовать все замечания в issue, указав проблему, расположение или компонент, требуемое исправление и приоритет.
2. Поставить `Need Fix`.
3. Если исправление однозначно следует из замечаний, требований issue и актуального плана, автоматически начать новый цикл с этапа `Planning`.
4. Если дальнейшая реализация зависит от выбора пользователя между несколькими допустимыми вариантами или требует изменения согласованных требований, описать варианты и их последствия в issue и приостановить работу до ответа пользователя.

#### Если замечаний нет

1. Назначить нового агента, не выполнявшего реализацию и ревью.
2. Убедиться, что проверенный HEAD совпадает с текущим HEAD ветки.
3. Синхронизировать локальную `main` с удалённой и при её изменении повторить необходимые итоговые проверки.
4. Смержить ветку задачи в `main` и убедиться, что merge завершился успешно.
5. Удалить замерженную ветку задачи локально и на GitHub, затем запушить изменения `main`.
6. Определить целевую версию следующей сборки или релиза, в которую войдёт исправление, и опубликовать её в комментарии issue. Не указывать версию последнего уже собранного APK, если исправление в него ещё не входит.
7. Поставить `QA`. Не закрывать issue и не ставить `Done` до завершения QA.

Если прямой merge или push запрещён правилами GitHub, создать PR из ветки задачи в `main` и указать ссылку в issue. До фактического слияния не переходить к `QA`. После слияния удалить замерженную ветку локально и на GitHub, синхронизировать локальную `main`, запушить необходимые изменения, определить целевую версию следующей сборки или релиза, в которую войдёт исправление, опубликовать её в комментарии issue и поставить `QA`. Не указывать версию последнего уже собранного APK, если исправление в него ещё не входит. Issue не закрывать и `Done` не ставить до завершения QA.
