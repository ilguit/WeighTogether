# Release-note fragments

Этот каталог хранит небольшие YAML-фрагменты, из которых последующая релизная
автоматизация соберёт историю изменений. Один фрагмент описывает один
самостоятельный результат работы по GitHub issue. Каталог и локальный валидатор
не обращаются к GitHub API: номер issue и содержание проверяются только по имени
файла и YAML.

## Когда создавать фрагмент

На стадии `Planning` определите и запишите в плане видимость и тип будущего
фрагмента: пользовательский (`userVisible: true`, поле `text`) или технический
(`userVisible: false`, поле `reason`). Сам файл на стадии `Planning` создавать не
нужно и нельзя. Создайте его во время `Coding`, а перед переходом в
`Ready for Review` запустите:

```bash
.github/scripts/validate-release-note-fragments.sh
```

Если после ревью работа продолжается, обновите существующий фрагмент этой работы.
Новый фрагмент для того же issue нужен только для отдельного изменения, которое
должно стать отдельным пунктом релизных заметок. Валидатор допускает несколько
фрагментов с одним номером issue, но имена файлов должны быть разными.

## Имя и схема

Имя должно иметь вид `<positive-issue>-<lowercase-slug>.yaml`, например
`24-release-note-fragments.yaml`. Номер — положительное целое без знака и ведущего
нуля; slug состоит из строчных латинских букв, цифр и одиночных дефисов. Расширение
строго `.yaml`. Номер в имени обязан совпадать с полем `issue`.

Документ должен быть единственным YAML mapping в файле. Разрешены только поля:

- `issue` — обязательное положительное целое число;
- `userVisible` — обязательный YAML boolean (`true` или `false`, не строка);
- `text` — обязательная непустая строка для пользовательского изменения; должна
  содержать минимум два русских Unicode-токена, в каждом из которых есть минимум
  две буквы `А–Я`, `а–я` или `Ё/ё`; combining marks внутри токена разрешены.
  Поле запрещено для технического изменения. Латинские названия продуктов и
  цифры рядом с русской фразой
  разрешены;
- `reason` — обязательная непустая строка для технического изменения и запрещена
  для пользовательского;
- `suppressReleasedChange` — необязательный YAML boolean, допустимый только для
  технического фрагмента. Значение `true` явно удаляет ранее выпущенный
  пользовательский текст этого issue из сформированной истории; по умолчанию
  равно `false`;
- `flavors` — устаревший необязательный фильтр, сохраняемый для совместимости с
  уже выпущенной историей. Для новых фрагментов поле не указывайте: приложение
  теперь имеет единственную сборку. Парсер принимает только значение `personal`.

Если `flavors` отсутствует, изменение относится к поддерживаемой сборке.
Не добавляйте поле в новые фрагменты, неизвестные поля, повторяющиеся YAML-ключи,
aliases или несколько YAML-документов. В каталоге разрешены только корректные фрагменты и два
зарезервированных служебных файла: `README.md` и `template.yaml.example`.
Фрагмент должен быть обычным файлом (symbolic links запрещены), содержать
корректный UTF-8 и занимать не более 65536 байт. Русские слова учитываются только
как отдельные Unicode-слова: смешанная запись вроде `абHealthвг` не считается
русской фразой, а combining marks не разделяют один токен на несколько слов и не
считаются самостоятельными буквами.
Для защиты от подмены путей валидатор требует от файловой системы поддержку
Java `SecureDirectoryStream`; на провайдере без неё проверка завершается с ясной
ошибкой, небезопасный fallback не используется.

Пользовательский пример:

```yaml
issue: 42
userVisible: true
text: Исправлена синхронизация новых измерений
```

Технический пример:

```yaml
issue: 24
userVisible: false
reason: Добавлена локальная проверка фрагментов релизных заметок
```

Начните с `template.yaml.example`, удалите неподходящую ветку `text`/`reason`,
затем переименуйте копию по правилу выше.

## Связь с историей версий

Issue #24 определяет формат, локальную проверку и правила ведения фрагментов.
Генератор из issue #25 собирает из них Kotlin-каталог и канонический JSON, а
проверки issue #26 блокируют неполную историю в Gradle и выпускном workflow.
Версии, созданные до введения фрагментов, один раз перенесены в закрытый baseline
по контракту `.release-history/README.md`; добавлять туда новые выпуски нельзя.
История показывает только явно выпущенные версии: обычная APK-сборка не создаёт
релизную границу. В обычной сборке незатегированные пользовательские фрагменты
после последнего выпущенного тега отображаются отдельно как «Последние изменения»;
они не создают новую версию. После явного release workflow эти изменения входят
в новую выпущенную версию, а отдельный блок становится пустым. Если уже выпущенная
работа технически переносится через новый диапазон, используйте содержательный
`reason` и `userVisible: false`: обычный технический carryover-маркер не меняет
ранее выпущенную историю и не создаёт новый пункт релизных заметок. Только когда
нужно явно удалить прежний пользовательский текст этого issue из всех
сформированных разделов истории, добавьте к техническому маркеру
`suppressReleasedChange: true`.
