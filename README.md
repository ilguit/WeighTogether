# Xiaomi Scale Sync

Xiaomi Scale Sync — локальное Android-приложение для автоматического получения
новых измерений с весов Xiaomi Mi Body Composition Scale 2 (`XMTZC05HM`) по
Bluetooth Low Energy. Приложение сохраняет результаты на устройстве, рассчитывает
показатели состава тела и передаёт поддерживаемые данные в Health Connect.

## Возможности

- принимает завершённые измерения с корректными значениями веса и импеданса;
- привязывается к выбранным весам и игнорирует данные от других устройств;
- рассчитывает BMI, долю жира и воды, мышечную и костную массу, белок,
  висцеральный жир, BMR, метаболический возраст и безжировую массу;
- хранит измерения и рассчитанные показатели в локальной базе данных;
- предотвращает появление повторных записей;
- передаёт вес, процент жира, массу воды, костную и безжировую массу, а также BMR
  в Health Connect;
- продолжает фоновое сканирование после перезагрузки устройства, обновления
  приложения и повторного включения Bluetooth;
- предоставляет режим повышенной надёжности с постоянным уведомлением для
  устройств, ограничивающих фоновую работу приложений.

Приложение не требует аккаунта Xiaomi, Zepp Life или собственного сервера и не
запрашивает доступ в интернет. Все данные хранятся в приватном хранилище
приложения и передаются только в Health Connect после явного разрешения
пользователя.

Персональная версия рассчитана на одного пользователя и одни активные весы. Она
обрабатывает только новые измерения и не импортирует историю из Zepp Life.
Прямая запись в Huawei Health в персональной версии не поддерживается.

Показатели состава тела являются оценками, рассчитанными по формулам
биоимпедансного анализа, и предназначены для наблюдения за тенденциями.
Приложение не является медицинским изделием и не должно использоваться для
диагностики или лечения.

## Резервное копирование

В разделе настроек можно экспортировать резервную копию и импортировать её в
режиме объединения или полной замены. Файл представляет собой JSON в формате
`scalesync-backup` версии `1`. В него входят аккаунты и профили, сохранённые
измерения вместе с рассчитанными показателями и состояниями синхронизации,
настройки распознавания веса, выбранные весы, режим надёжности и наборы графиков.

В резервную копию не входят ожидающие обработки пакеты и их служебные отметки,
разрешения и учётные данные Health Connect или Huawei Health, а также записи,
которые находятся только во внешних health-сервисах. Импорт сам по себе не
запрашивает разрешения и не извлекает данные из этих сервисов.

При объединении существующие локальные данные и настройки сохраняются, а новые
аккаунты и измерения добавляются. Полностью совпадающие записи пропускаются;
различающиеся записи с тем же идентификатором, именем аккаунта, отпечатком или
хешем дедупликации считаются конфликтом, и импорт не применяется. При полной
замене локальные аккаунты, измерения, настройки и очередь ожидающих измерений
заменяются содержимым файла. Перед применением приложение показывает результат
импорта и требует подтверждения.

Резервная копия содержит чувствительные данные о здоровье и профиле. Файл не
шифруется приложением: храните и передавайте его как конфиденциальный документ,
используя защищённое хранилище и шифрование устройства или выбранного сервиса.

## Разработка

Приложение полностью пишется и развивается в автоматическом режиме программными
ИИ-агентами.

### Выпуск персонального APK

Ручной workflow `Build personal APK` загружает APK и JSON-файл метаданных одним
artifact, а затем создаёт annotated Git-тег `apk/<versionName>`. Тег всегда
указывает на `github.sha`, из которого собран APK. Метаданные содержат базовый
`versionName`, полную variant-версию с суффиксом `-personal`, SHA коммита и
предыдущий достижимый release tag (либо `null` для первого тегированного выпуска).

Повторный запуск для той же версии и того же SHA безопасен: существующий тег
считается успешным результатом и второй тег не создаётся. Использование той же
версии на другом SHA блокируется до сборки. Если artifact успел загрузиться, но
отправка тега завершилась инфраструктурной ошибкой, следует повторить workflow
на том же SHA. Для выпуска нового коммита необходимо сначала увеличить
`versionName` и `versionCode`.

Перед упаковкой APK Gradle автоматически запускает блокирующую проверку release
metadata для собираемого variant. Проверка сопоставляет Git-фрагменты с
версионированной историей релизов и останавливает сборку, если фрагмент потерян,
продублирован или не согласован с историей. Та же проверка выполняется в ручном
GitHub Actions workflow до загрузки artifact и создания тега. Она подключена к
задачам упаковки APK, но не замедляет unit-тесты и lint.

Локально связь preflight с Gradle task graph проверяется командой:

```bash
.github/scripts/test-release-metadata-wiring.sh
```

Локальная проверка логики тегов не публикует ничего в основной репозиторий и
работает с временными bare-репозиториями:

```bash
.github/scripts/test-release-apk-tag.sh
```

Пример JSON-файла рядом с APK:

```json
{
  "commitSha": "0123456789abcdef0123456789abcdef01234567",
  "previousReleaseTag": "apk/0.1.5",
  "variantVersionName": "0.1.6-personal",
  "versionName": "0.1.6"
}
```

### Фрагменты релизных заметок

Каждая задача во время реализации добавляет пользовательский или технический
YAML-фрагмент в `.release-notes/`. Полный контракт и примеры находятся в
`.release-notes/README.md`. Перед передачей задачи на ревью запустите локальную
проверку, не использующую GitHub API:

```bash
.github/scripts/validate-release-note-fragments.sh
```

### Встроенная история версий

История на экране приложения генерируется при сборке из достижимых annotated-тегов
`apk/<version>`, релизных фрагментов и закрытого исторического baseline в
`.release-history/baseline.yaml`. Генератор создаёт Kotlin-каталог для интерфейса
и канонический `res/raw/app_release_history.json`; оба файла относятся к конкретным
variant и HEAD. Исторические версии 0.1.1–0.1.6 хранятся только в baseline, новые
выпуски добавляются через теги и фрагменты — расширять baseline нельзя.

Локально результат для personal debug можно проверить командой:

```bash
./gradlew :app:generatePersonalDebugReleaseHistory
```

Для воспроизводимой генерации нужен полный first-parent Git history и все теги.
Shallow checkout блокируется до вычисления release range; восстановите историю
командой `git fetch --unshallow --tags` (или выполните полный fetch с tags, если
репозиторий уже не помечен shallow). Previous release определяется только по
annotated `apk/*` tag на first-parent цепочке: tag на влитой side branch не
считается границей выпуска. Генератор также требует чистое состояние
отслеживаемых файлов.
